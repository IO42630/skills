Recursive totals: one list, one answer

By the end, you will be able to trace a nested-list total and explain exactly how a child's returned number becomes part of its parent's total.

Spend about 1 minute on the idea, 4 on the trace, 2 on the mistake, 2 on practice, and 1 on the takeaway. Use paper for the practice before opening the answers.

A return gives the waiting call an answer

For a flat list, you already know the job: start at zero, loop through the numbers, and add each one. A nested list changes just one decision. When an item is itself a list, you need its total before you can add it.

Ask the same function to total that smaller list. When it returns a number, add that number to the current total. Recursion is a function calling itself; it still uses the same loops and returns you know.

We will use [2, [3, 4]]. Its answer is 9. The useful question is not what the answer is, but how the inner 7 gets back to the call that has already counted 2.

Follow two calls, not one shared total

This is runnable Python for finite nested lists of integers, with no list containing itself directly or indirectly. isinstance(item, list) asks whether the item is a list. Input validation is omitted so we can focus on the return.

def total(items):
    result = 0
    for item in items:
        if isinstance(item, list):
            result += total(item)
        else:
            result += item
    return result

total([2, [3, 4]])  # returns 9

Call the outer call the parent and the call it starts the child. These are labels for two executions of the same function, not different functions. Each call has its own items, result, and loop position.

  1. Parent starts: its items is [2, [3, 4]] and its result starts at 0. The first item is the integer 2, so the parent's result becomes 2.
  2. Parent reaches the list: its next item is [3, 4]. At result += total(item), the parent needs the value of total([3, 4]). It waits here with its result still 2; it has not added anything for this item yet.
  3. Child starts: its items is [3, 4]. Its own result starts at 0, not at the parent's 2. It adds 3, then 4, giving 7.
  4. Child finishes: its loop is over, so return result returns 7 to the waiting parent. It ends this child call, not the parent call.
  5. Parent resumes: the waiting expression total(item) now supplies 7. The pending addition is therefore 2 + 7, making the parent's result 9. Its loop ends and it returns 9.
Parent: total([2, [3, 4]])   result: 0 → 2 → waits → 9
Child:       total([3, 4])   result: 0 → 3 → 7
                                          returns 7 to parent

The child's return does not reach into the parent's local variable. The parent changes its own result because it adds the returned value.

Why does this stop?

Each recursive call takes one contained list, going deeper into the finite nesting. A list containing only numbers makes no more calls: its loop simply adds and returns. That is the stopping case, often called the base case. An empty list also stops immediately: its loop runs zero times, so total([]) returns 0. This code needs no separate base-case if.

return result belongs after the loop. Returning inside the loop would finish that call before it had processed the remaining items.

Visiting a child is not adding its answer

Suppose you keep the same function but change only its list branch:

if isinstance(item, list):
    total(item)  # changed line: no addition

Diagnose it before revealing: What would the changed function return for [2, [3, 4]]? Would the child still calculate 7? Explain why those two answers can differ.

Reveal the diagnosis

The parent returns 2. The child still calculates and returns 7, because its two items are numbers. But the parent calls the child without using its returned value. Nothing adds that 7 to the parent's result.

The repair is result += total(item). Calling a function does not automatically collect its answer. Recursion follows the same rule as any other function call.

Check the changed-list trace

The parent calls the same function on the contained list and adds its returned number. It has its own result, separate from the child's.

Parent adds 1:             result = 1
Child totals [2, 3]:       returns 5
Parent adds child's 5:    result = 6
Parent adds last item 4:  result = 10
Parent returns:           10

The parent processes 4 after the child returns. The child ends only its own call. The parent resumes at the waiting addition, then continues its loop to the next item.

If you got 5, you may have mistaken the child's answer for the whole answer. If you got 6, you may have stopped the parent too soon. Keep the parent's remaining loop items visible while the child runs.

Check the empty-list case

The empty child starts with result = 0, visits no items, and returns 0. The parent adds that zero, then adds 5, and returns 5. A list does not need any numbers to produce a usable answer.

The rule to keep

Each call totals its own list. A parent waits for a child's number, adds that number, then continues its own loop. Separate calls have separate local totals; the return value is what crosses back.

This version assumes integers or nested lists, finite nesting, and no circular references. Other item types need a defined policy. Extremely deep nesting can exceed Python's recursion limit; this is a small example for understanding the mechanism, not an unrestricted input handler.
