A recursive total comes back one call at a time

Your goal: trace a nested-list total and explain exactly how a returned child total becomes part of its parent's total.

You already know Python loops and function returns. We will use those same ideas: a recursive call is just another function call, made to the same function.

One list, one local total

Suppose the input is [2, [3, 4], 1]. A loop can add 2 and 1 directly. The middle item is a list, not a number. Ask another call to total that list, then add the number it returns.

Each call totals its own list. When it encounters a child list, it pauses while a child call totals that list. The child returns a number; the parent adds that number and continues its loop.

Parent means the call that requests the work. Child means the call it starts. These are calls to the same function, not two different functions.

def nested_total(items):
    total = 0
    for item in items:
        if isinstance(item, list):
            total += nested_total(item)
        else:
            total += item
    return total

isinstance(item, list) asks whether this item is a list. If so, nested_total(item) returns its subtotal. Otherwise, this example assumes the item is an integer, which we can add directly.

Notice the position of return: it is after the loop. Each call returns only after it has handled every item in its own list.

Watch the handoff: [2, [3, 4], 1]

Call the outer call A and the call for [3, 4] B. These labels are just for our trace; the function does not need them.

  1. A starts. Its own total begins at 0. Its first item is 2, so A's total becomes 2.
  2. A reaches [3, 4]. To evaluate total += nested_total(item), Python must first obtain the number on the right. A waits with its total still 2; it has not reached 1 yet.
  3. B starts with [3, 4]. B has a new, separate total = 0. Adding 3 makes it 3; adding 4 makes it 7.
  4. B finishes its loop and returns 7. That return ends B, not A. Back in A, the waiting expression now has a number to add:
# In A, after B returns:
total += nested_total([3, 4])
# The child call has produced 7, so the addition is:
total += 7                 # A's total: 2 + 7 = 9

The two lines above show the same operation before and after the child result is known. They are not two additions to run.

  1. A resumes its loop. Its next item is 1, so its total becomes 10.
  2. A finishes and returns 10 to whoever called it.
# Two separate totals, not one shared variable:
A: 0 → 2 → waits → 9 → 10 → returns 10
B:         0 → 3 → 7 → returns 7 to A

Every call uses the name total, but each has its own local variable. Starting B at zero does not reset A. Returning 7 does not change A by itself; A's += is what incorporates that result.

The tempting mistake: calling without collecting

If the list branch were only nested_total(item), B would still calculate and return 7, but A would discard it. With the rest unchanged, A would return only 2 + 1 = 3. Doing the child work is not enough; the parent must use its result.

Where does the recursion stop?

A call on [3, 4] makes no child calls: it adds its numbers and returns. A call on [] has no loop iterations, so it immediately returns its initial total, 0. These are the stopping cases, often called base cases; this function handles them through the loop rather than a separate special-case return.

For a finite list structure with no cycles, descending into child lists eventually reaches these cases. Then the results travel back up, one return at a time.

1. Reconstruct the rule · 1 minute

Without looking back, describe what a call does with a number, what it does with a list, and when it returns. Then explain why calling the child without adding its return value loses part of the total.

Reveal the rule and reasoning

Start a local total at zero. Add each number directly. For each list, call the same function on that list and add the returned subtotal. Return the local total only after the loop finishes.

A child's local total is separate from its parent's. A bare call can calculate a correct subtotal but discard it. The parent must combine the returned number with its own total.

Reveal the trace and compare your reasoning
  1. The outer call adds 4, then waits with its total at 4.
  2. The call on [1, [2]] adds 1, then waits with its own total at 1.
  3. The call on [2] adds 2 and returns 2 to the call on [1, [2]], not directly to the outer call.
  4. The middle call adds that 2 to its 1 and returns 3. The outer call then adds this returned 3 to its 4, reaching 7.
  5. The call on [] returns 0. Adding it leaves the outer total at 7.
  6. The outer call adds its last number, 3, and returns 10.

If you sent 2 straight to the outer call: returns go to the immediate caller. The middle call must first combine 1 + 2 and return that subtotal.

If you reset the outer total: each new call starts its own total at zero; the waiting call keeps its previous value. If you stopped at 7, remember that the outer loop resumes after the child returns and still processes 3.

Keep this rule

Number → add it. List → ask a child call, add its returned subtotal. End of this list → return this call's total.

Scope: this teaching function expects integers and nested lists, with a finite, cycle-free structure. It does not validate other inputs. Extremely deep nesting can exceed Python's recursion limit even without a cycle; solving that is a separate lesson.
