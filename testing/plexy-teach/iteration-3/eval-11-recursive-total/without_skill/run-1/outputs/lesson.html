Ten-minute Python lesson · loops and returns are enough

Nested lists, one total

Recursion is a function asking another call of itself to solve a smaller version of the same problem. The useful part is not the self-call alone: it is what comes back, and what the waiting caller does with it.

By the end, you will trace a nested-list total, explain where each returned number goes, and finish the function yourself.

Read in order. Before opening each answer, make a prediction on paper or in your head. No Python installation is needed; all answers are included.

Minute 0–1 · Start with the job

1. Every list owes us one number

Our function should add every number, however deeply it is nested:

nested_total([2, [3, [4]], 5])  # should return 14

The numbers are 2, 3, 4, and 5. Brackets group them; brackets do not contribute a value.

The promise: Give nested_total a list; it returns a single number: the sum of every number inside that list, including inside its sublists.

We assume a finite nested structure containing only Python lists and numbers, with no list containing itself. Handling strings, other containers, or extremely deep nesting is outside this lesson.

Predict: What number should nested_total([3, [4]]) return?

Check the smaller list's answer

7. If that smaller list can give us 7, the outer list only needs to add 2 + 7 + 5. We can treat a completed sublist exactly like one number.

Minutes 1–3 · Connect recursion to a familiar loop

2. Keep the loop; ask for a subtotal

A loop handles the items at the current level. When an item is itself a list, another call handles that list's level.

def nested_total(items):
    total = 0
    for item in items:
        if isinstance(item, list):
            total += nested_total(item)
        else:
            total += item
    return total
  • total = 0: start a subtotal for this call.
  • isinstance(item, list): ask whether this item is a sublist.
  • For a number, add it directly. For a list, call the same function with that sublist, then add its returned number.
  • return total is outside the loop: return only after handling every item.
Read total += nested_total(item) as: “Wait for this sublist's total, then add it to my total.” It does not add the list itself.

What makes it stop?

For [], the loop runs zero times and the function returns 0. That is a base case: an input answered without another recursive call. A list of only numbers also needs no recursive calls.

Each recursive call receives an actual sublist, one level further down. In our finite, non-circular structure, you eventually reach lists with no further sublists. Then the calls return, working back outward.

Predict: Does nested_total([6, 2]) call itself? What about nested_total([])?

Check when no self-call is needed

Neither calls itself. The first adds two numbers and returns 8. The second adds nothing and returns 0. Recursion happens only when the loop encounters a list.

Minutes 3–6 · Follow the waits and returns

3. Three calls, three separate subtotals

Trace nested_total([2, [3, [4]], 5]). We will nickname its calls A, B, and C. These are not different functions; they are three executions of the same function.

A: nested_total([2, [3, [4]], 5])
    B: nested_total([3, [4]])
        C: nested_total([4])

Each call has its own items, item, and total. A paused call keeps its current subtotal and its place in its loop. Starting B does not reset A's subtotal.

Execution order: go inward to calculate; return outward to combine.
StepActive call and actionWaiting calls
1A starts at 0; adds 2. A's total is 2.None.
2A meets [3, [4]] and starts B.A waits at total 2; it has not reached 5.
3B starts at 0; adds 3. B's total is 3.A still has 2.
4B meets [4] and starts C.B waits at 3; A waits at 2.
5C starts at 0; adds 4. C's total is 4.B has 3; A has 2.
6C's loop ends. C returns 4 to B.A still waits at 2.
7B resumes its pending addition: 3 + 4 = 7. B's loop ends; B returns 7 to A.A is about to resume.
8A resumes its pending addition: 2 + 7 = 9.No inner calls remain.
9A continues its loop to 5: 9 + 5 = 14.None.
10A's loop ends. A returns 14 to whoever called it.Done.

Pause and explain: When C returns 4, why doesn't A immediately add that 4?

Check where a return goes

C was called by B, so C's return replaces the call expression inside B. B adds 4 to its own 3. Only when B finishes does A receive B's complete subtotal, 7.

A return goes to the immediate caller, not automatically to the outermost call. The waiting calls behave like a stack: the most recently started call finishes first.

The key distinction: The loop moves across one list. A recursive call moves down into one sublist. Returning brings a subtotal back up.
Minutes 6–8 · Try the model yourself

4. An empty list still returns a number

nested_total([1, [2, []], 3])

Before opening the answer, fill in these four checkpoints:

  1. The innermost call on [] returns ___.
  2. The call on [2, []] returns ___.
  3. The outer call's total, immediately after adding that subtotal, is ___.
  4. After processing its final item, the outer call returns ___.
Need a hint before the answer?

The empty-list call starts its own total at zero. Its loop does nothing, but it still reaches return total. Add that returned number to the waiting caller's subtotal.

Check all four checkpoints
  1. 0: no items to add.
  2. 2: the middle call combines 2 + 0.
  3. 3: the outer call combines its previous 1 with the returned 2.
  4. 6: it then adds the final 3.

If you predicted None for the empty list, follow the indentation: return total executes even when the loop never starts. If you predicted 2 at checkpoint 3, remember that the outer call kept its earlier 1.

Minutes 8–10 · Complete it and catch two mistakes

5. Your final challenge

Fill in the blanks without looking back. Then predict the result of the call below and explain, in one sentence, why each sublist's numbers are counted only once.

def nested_total(items):
    total = 0
    for item in items:
        if isinstance(item, list):
            total += __________
        else:
            total += __________
    return __________

nested_total([4, [1, [2]], 3])
Check the completed function and prediction

The blanks are nested_total(item), item, and total.

The call on [2] returns 2. The call on [1, [2]] returns 1 + 2 = 3. The outer call returns 4 + 3 + 3 = 10.

Each call loops over only its own list's immediate items; for a sublist it adds the returned subtotal once, rather than separately looping over those same inner numbers itself.

Two small changes that break the promise

A. Suppose the list branch says only nested_total(item), with no total +=. What would the final challenge return?

Check mistake A

7. The recursive work still happens, but its returned numbers are discarded. The outer call adds only its direct numbers, 4 and 3. A function call does not magically update another call's local total.

B. Suppose return total is moved inside the loop, after the if/else. What would the same input return?

Check mistake B

4. The outer call returns after its first item; it never reaches the sublist or the final 3. An empty list would also fall through without returning a number. Keep the return outside the loop.

Takeaway: “I total this level. For each sublist, I wait for its total and add it. After my loop finishes, I return my total to my caller.”

Exit check: Can you explain why nested_total([[], [5]]) returns 5, and identify which call receives each inner return?

Check the exit explanation

The outer call receives 0 from its call on [], then receives 5 from its call on [5]. It adds both to its own starting zero and returns 5. Both inner calls return directly to the outer call because both were started by it.

If you can explain those return destinations, you have the central model. If not, revisit steps 6–8 in the trace and keep each call's subtotal separate.
