A race condition is a bug that occurs when a program's behavior depends on the unpredictable timing or ordering of concurrent operations, usually when multiple threads or processes access shared data at the same time. The classic example is two threads both doing "read a counter, add 1, write it back." If both read the value 0 before either writes, the counter ends up as 1 instead of 2, even though two increments happened. The operations individually look correct; the problem is that they interleave.

One standard way to prevent race conditions is mutual exclusion: protect the shared resource with a lock (mutex). Each thread must acquire the lock before entering the critical section and release it afterward, so only one thread can manipulate the shared data at a time. This serializes access and makes the increments happen in a well-defined order, guaranteeing the counter reaches 2.

Related alternatives include using atomic operations or thread-safe data structures for simple cases, or avoiding shared mutable state entirely by giving each thread its own copy or communicating through message passing. But locking around the critical section is the most common, general-purpose fix.
